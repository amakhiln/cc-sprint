# Rubric Walker Review — ARCHITECTURE-SPINE.md (2026-08-25 amendment)

Reviewed: `_bmad-output/planning-artifacts/architecture/architecture-pm-2026-08-12/ARCHITECTURE-SPINE.md`
Focus: AD-7, AD-8 (new), AD-3 (amended REST correction), AD-1 (domain-import-direction claim), plus a full pass against the checklist.

## Verdict

The spine's AD-3 REST correction is accurate and fully ratified by the actual `infrastructure/youtrack/` code, and AD-1's domain-import-direction claim holds against the real `domain/` tree — but AD-7/AD-8, the two genuinely new decisions, contain one real architectural contradiction (an unacknowledged infrastructure-to-infrastructure import) and one unenforced core guarantee (the anti-hallucination "grounding" rule has no verification mechanism, only an LLM instruction), plus a structural dimension — conversation/session state — left completely undecided despite the feature being explicitly conversational; none of these are cosmetic, and all three would let two independently-built stories diverge exactly the way the spine's own stated purpose says it exists to prevent.

## Findings

- **[CRITICAL] AD-8 introduces an unacknowledged infrastructure→infrastructure import, contradicting the established Ports & Adapters pattern.** AD-8's rule says `infrastructure/query-assistant/` "calls `infrastructure/youtrack-mcp/`'s registered tools (AD-7) for YouTrack-sourced answers, and calls `domain/`'s existing functions... directly for app-data answers — permitted under AD-1's existing infrastructure→domain import direction; no new dependency rule is introduced." That justification only covers the *domain* call. The call to `infrastructure/youtrack-mcp/` is a different adapter package calling another adapter package directly — a pattern that does not exist anywhere in the current codebase (verified: every existing `infrastructure/*` file imports only from `domain/`, `@/app/generated/prisma`, or its own sibling file within the same adapter folder — grep of all `infrastructure/**/*.ts` imports shows zero cross-adapter-folder imports today). The codebase already has the idiomatic fix sitting right there: every other adapter is wired through a domain-defined port (`YouTrackConfigRepo`, `YouTrackIssuesPort` in `domain/youtrack.ts`, implemented in `infrastructure/`, injected at the `app/` composition root) — AD-8 could define a `domain`-level tool-provider port the same way and have `app/api/assistant/route.ts` inject the concrete `youtrack-mcp` adapter, instead of one infra module importing another. As written, one implementer building `query-assistant/` from the story alone would reasonably import `youtrack-mcp/` directly (matching the literal prose); another, familiar with the codebase's existing port pattern, would define a port instead. That's exactly the "two independently-built units diverge" failure mode AD-1 exists to prevent, now reopened by AD-8.

- **[CRITICAL] AD-8's central anti-hallucination guarantee has no enforcement mechanism — it is a prompt instruction, not a structural rule.** AD-8 exists specifically because "the assistant free-generating a plausible-looking number... is a hallucination risk no other FR carries." Its Rule states "every numeric or factual claim in an answer must trace to an actual return value... the LLM is never allowed to state a figure it wasn't just handed." Every other AD in this spine enforces its guarantee at the code/type/DB level (banned imports, a DB constraint, an enum, a soft-delete flag) — something a compiler, linter, or constraint can actually reject. AD-8's guarantee has no such mechanism specified: no structured/templated response construction, no post-generation verifier that checks every number in the LLM's output against the set of numbers actually returned by a tool/domain call, nothing. As written it relies entirely on the LLM following an instruction, which is not a "Rule [that] is enforceable and actually prevents its stated divergence" — it's the one guarantee in the whole document that a well-behaved implementer *and* a careless one both satisfy equally well from the prose alone, because nothing here can be checked. This is worth flagging back to the PM/architect explicitly since it's the load-bearing guarantee of the whole feature.

- **[HIGH] "PM-session-scoped" (AD-8's own title) is never defined, and tension exists with AD-5's "no session... model" statement.** AD-8 is titled "...PM-session-scoped" but the Rule paragraph never says what a "session" is here — no session id, no TTL, no storage. Nothing in the Structural Seed's ERD or Stack table adds any conversation/message/history entity or store (compare: every other stateful concern in this app — Sprint, Leave, Holiday, even the `ShareToken` singleton — got an explicit table). Given the feature is literally called a "Conversational Query & Reporting Assistant" (Capability Map §4.7), multi-turn continuity is presumably intended, yet nothing says whether history is server-held (where? in-memory, keyed by what?), client-resent per request, or absent entirely (single-turn only). This collides with AD-5's explicit "no login, session, or user-account model" — if there truly is no session concept anywhere in the app, AD-8 borrowing the word "session" without defining it is either a contradiction or an undefined term, and two implementers will build genuinely different behavior (one stateless single-turn assistant vs. one that fakes a session via a browser-generated id) from the same prose.

- **[MEDIUM] Sending internal roster/allocation/leave data to a third-party LLM provider is never decided, deferred, or logged as an open question.** AD-8 has the domain layer's data (capacity, allocation breakdowns, team member names) flow into an LLM's context via tool results so it can be summarized/answered over. No AD, Deferred entry, or Open Question addresses what's acceptable to send to Anthropic's API (or any provider) — team member names and allocation percentages are the kind of data a company might have a view on exporting to a third party. This is a structural dimension ("feature altitude" clearly owns "what data crosses the trust boundary to an external API") left completely silent rather than decided/deferred/flagged.

- **[MEDIUM] The Consistency Conventions table's error-shape rule isn't reconciled with the new streaming route.** "Data & formats" states Server Actions return `{ok:true,data}` / `{ok:false,error}` "so the UI has one uniform error-handling shape." `app/api/assistant/route.ts` is explicitly flagged `[ASSUMPTION]` as a Route Handler "to support streaming a chat response" — a streaming body structurally cannot return that discriminated-result shape. AD-8 does separately describe an error posture ("a plain inline statement in the response"), which is good, but the standing Conventions table's "one uniform shape" claim is now false for this route and nothing says so — a future reader of the Conventions table alone would expect the assistant route to follow it.

- **[LOW] Stale MCP-referencing comments in `domain/youtrack.ts` contradict AD-3's amendment and could mislead a story implementer**, even though the spine itself is accurate. `domain/youtrack.ts` still says "`infrastructure/youtrack/client.ts` implements this against the actual `@modelcontextprotocol/client` SDK" (twice, on `YouTrackConnectionTester` and `YouTrackIssuesPort`) — this is now false; `client.ts`/`issues.ts` use `rest-client.ts` (`fetch` + bearer token), not the MCP SDK. Not a spine defect, but the spine's job of "ratifying reality" would be stronger if it flagged this drift for cleanup, since AD-7 is about to add a *second*, genuinely MCP-based adapter and stale comments claiming the *first* adapter is MCP-based are a real source of confusion between the two.

- **[LOW] `project-context.md` (the standing convention doc) is not updated for AD-7/AD-8's new adapters.** It still describes `infrastructure/` as only `db/` and `youtrack/`; it has no mention of `youtrack-mcp/` or `query-assistant/`, and doesn't carry forward the infra-to-infra import question raised above. Since `project-context.md` is the doc AGENTS.md/CLAUDE.md point agents to first, this is a documentation-sync gap worth closing alongside the CRITICAL finding above (once that's resolved, `project-context.md` should say whether infra-to-infra imports are or aren't allowed).

- **[LOW] No bound is stated on the Query Assistant's tool-call loop.** AD-8 describes "the tool-call loop" living in `infrastructure/query-assistant/` but no AD states a max-iterations/timeout bound for it. Given AD-8's own concern is runaway/ungrounded behavior, an unbounded tool-call loop is a small but real cost/latency risk left as an implementation detail rather than a decision.

## Checked and found clean

- **AD-3 REST description matches the real code exactly.** `infrastructure/youtrack/client.ts`, `issues.ts`, and `rest-client.ts` contain zero `@modelcontextprotocol/client` imports; all three use `fetch` + `Authorization: Bearer` via `restGet`, matching AD-3's amended prose point for point (no per-call handshake, direct REST shapes, no MCP dependency). `YouTrackConfig`'s three fields (`instanceUrl`, `projectId`, `authToken`) match both `domain/youtrack.ts` and the spine's ERD.
- **AD-1's domain-import-direction claim holds.** Every file in `domain/*.ts` (excluding `.selfcheck.ts` test files) imports only from other `domain/` files — zero imports from `app/` or `infrastructure/`, confirmed by grep across the whole `domain/` tree. Matches `project-context.md`'s stated rule verbatim.
- **Stack table versions are verified-current, not stale.** Next.js 16.3.0, React 19.2.8, Prisma/`@prisma/client` 7.9.1, and `@modelcontextprotocol/client ^2.0.0` all match the installed `package.json`/`node_modules` exactly. The one genuinely unconfirmed stack entry (Claude model choice for the assistant) is correctly tagged `[ASSUMPTION]` with a stated reason and a named point of confirmation.
- **AD-7's tool-allowlist mechanism is structurally enforceable.** Because the MCP client is only ever registered with the read-tool subset at registration time, the LLM has no way to invoke a tool it was never given — this is a real code-level guarantee, unlike AD-8's grounding claim (see CRITICAL finding above).
- **AD-4/AD-8 isolation is consistent and doubly-stated.** Both AD-4's rule and AD-8's rule (and the mermaid diagram's explicit "never reachable" dotted edge from `Share` to `Assistant`) agree that `app/share/[token]/` cannot reach the assistant route — no contradiction between the two ADs.
- **Deferred section itself carries no divergence risk.** Hosting/auth/multi-team/observability/CI/test-runner are all genuinely low-stakes or explicitly out of PRD scope; the one Deferred item that *could* cause divergence (AD-7's live MCP tool-list verification, PRD Open Question 4) is correctly sequenced ("do this before implementing Story work for FR-25/FR-26"), not left open-ended.
